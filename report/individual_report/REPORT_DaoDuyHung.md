### Documentation

The application coordinates the interaction between the language model and external tools.

For each user query, the LLM first generates a Thought and an Action. The Action is parsed and executed using the corresponding tool. The Observation is then appended to the conversation history before the LLM continues reasoning. This loop continues until the model generates a Final Answer or reaches the maximum iteration limit.

## II. Debugging Case Study (10 Points)

### Problem Description

During integration, the ReAct Agent repeatedly failed after entering the reasoning loop.

Two major issues were observed:

- `AttributeError: 'str' object has no attribute 'get'`
- Agent repeatedly attempted to parse Actions or terminated because no valid Action was returned.

### Log Source

Console log example:

```
Thought: I need to analyze the candidate first.

Action: analyze_cv["John"]

Observation: Candidate meets the requirements.

Thought: Schedule an interview.

Final Answer: John is qualified and can proceed to the interview stage.
```

Earlier failing log:

```
AttributeError: 'str' object has no attribute 'get'
```

### Diagnosis

The failures were caused by several integration problems:

- `config/test_cases.json` changed from a list into an object containing a `test_cases` field.
- The parser expected every LLM response to contain an Action.
- Tool names in the prompt and `AVAILABLE_TOOLS` were initially inconsistent.
- Gemini Free Tier API quota occasionally interrupted execution during testing.

### Solution

I fixed the issues by:

- Updating `load_test_cases()` to correctly load `data["test_cases"]`.
- Improving Action parsing and error handling.
- Synchronizing tool names between prompts and the tool registry.
- Adding `MAX_ITERATIONS` to prevent infinite loops.
- Implementing graceful fallback messages when no valid Action is generated.
- Adding throttling and timeout support for API calls.

## III. Personal Insights: Chatbot vs ReAct (10 Points)

### 1. Reasoning

The Thought step significantly improved the agent's reasoning process. Instead of generating an answer immediately, the agent could determine whether external information was required before responding.

### 2. Reliability

The ReAct Agent performed worse when:

- tool names were inconsistent,
- APIs were unavailable,
- external tools returned errors,
- or the LLM generated an invalid Action.

In these situations, a normal chatbot could still produce a fluent answer, while the agent depended on successful tool execution.

### 3. Observation

Observation served as feedback from the environment. After each tool execution, the returned information guided the next reasoning step, allowing the agent to make more accurate decisions instead of relying solely on internal knowledge.
